
# 🚕 Taxi Booking System — Complete Backend & Dashboard Requirements

## Technology Stack
- Frontend: Nuxt.js
- Backend: Spring Boot
- Payment Gateway: Stripe
- Database: PostgreSQL
- Cache & OTP Storage: Redis

---

# 1. System Overview

The application is a taxi booking platform operating primarily from Barcelona.

Users can:
- Book rides within Barcelona (IN_CITY)
- Book rides from Barcelona to another city (CITY_TO_CITY)
- View available cars with dynamically calculated fares
- Apply filters on the car selection page
- Complete online payments
- Receive booking receipts
- Track ride progress

The backend must:
- Calculate fares dynamically
- Manage drivers and cars
- Handle payments
- Store booking lifecycle
- Support scalability and future enhancements

The backend architecture must follow:
- SOLID principles
- Clean Architecture / Hexagonal Architecture
- Strategy Pattern for fare calculation

---

# 2. Core Application Flow

# CUSTOMER FLOW

## 2.1 Homepage Flow

User opens the application and enters:
- Pickup location
- Dropoff location
- Ride date & time

Frontend sends:
- Pickup coordinates
- Dropoff coordinates
- Distance
- Ride type

Passenger count is NOT sent from the first page.

---

## 2.2 Ride Type Determination

Ride type values:
- IN_CITY
- CITY_TO_CITY

Rules:
- If pickup and destination are inside Barcelona → IN_CITY
- Otherwise → CITY_TO_CITY

Frontend may send ride type, but backend must validate it.

---

## 2.3 User Clicks “Book Now”

After clicking “Book Now”:

Backend performs the following:
1. Determines ride type
2. Fetches all active and available cars
3. Calculates fare for every car
4. Attaches calculated fare to each car
5. Returns complete car list to frontend

Frontend then opens the car selection page.

---

## 2.4 Car Selection Page

The second page displays:
- Car name
- Passenger capacity
- Car type
- Calculated fare
- Vehicle image
- Ride type
- Availability status

Example:
| Car | Capacity | Fare |
|---|---|---|
| Mercedes Vito Van | 7 Passenger | €55 |
| Tesla Model S | 4 Passenger | €50 |

---

## 2.5 Car Filters

Frontend must provide filters such as:
- Passenger capacity
- Car type
- Price range
- Luxury / Standard
- Electric vehicles
- Van / Sedan / SUV

Filtering can initially be frontend-based and later moved to backend APIs for scalability.

## 3.3 Backend Car Fare Flow

When frontend calls:
POST /api/v1/rides/cars

Backend flow:
1. Validate pickup and dropoff
2. Determine ride type
3. Fetch all active cars
4. Calculate fare for every car
5. Attach calculated fare
6. Return enriched car list

Passenger filtering is not applied initially because passenger count is not yet selected.

---

# 4. Fare Calculation Module

## 4.1 SOLID-Based Fare Calculation Design

Fare calculation logic must remain separated using:
- Strategy Pattern
- Interface-based design

Recommended structure:
- FareCalculationStrategy
- InCityFareCalculationStrategy
- CityToCityFareCalculationStrategy

Benefits:
- Easier future modifications
- Supports dynamic pricing
- Follows Open/Closed Principle
- Improves maintainability and testing

---

# 5. IN_CITY Fare Calculation

## 5.1 Distance-Based Pricing

Each car has:
- A base fare valid up to 27 KM

## 5.2 Additional Distance Logic

After 27 KM:
- Additional amount charged every 3 KM block
